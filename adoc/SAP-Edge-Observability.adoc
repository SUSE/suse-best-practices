
# tag::intro[]
This chapter describes how to install {so} on a Kubernetes cluster and use it to observe a {shyb} environment running on a separate cluster.

This topology is recommended for production and proof-of-concept deployments because it keeps the monitoring backend independent from the application workload, simplifies troubleshooting, and makes it easier to preserve the visibility stack during maintenance or upgrades.

The installation procedure below follows the official {so} installation flow documented at https://documentation.suse.com/cloudnative/suse-observability/latest/en/installing-suse-obs.html.

# end::intro[]

# tag::prerequisites[]
=== Prerequisites

Before installing {so} on the monitoring cluster, ensure the following requirements are met:

* A supported Kubernetes cluster is available for the observability stack.
* You have `kubectl` access to the monitoring cluster.
* The cluster has a working storage class for the Observability backend.
* A valid {so} license is available.
* Helm 3 is installed on the workstation or cluster shell that is used for installation.
* You have a hostname or FQDN that is reachable from your users, such as `https://observability.example.com`.
* The {shyb} cluster can reach the monitoring cluster if you use the agent-based flow.
* MetalLB makes {so} available outside the cluster.
* {cm} manages the certificates.

# end::prerequisites[]

# tag::pre-mon[]
=== Prepare the monitoring cluster

Open a shell on the cluster and add the {so} Helm repository:

[source, bash]
----
helm repo add suse-observability https://charts.rancher.com/server-charts/prime/suse-observability
helm repo update
----

You can inspect the chart before installation if needed:

[source, bash]
----
helm show values suse-observability/suse-observability
----

# end::prep-mon[]

# tag::values[]
=== Create a values file

Create a `values.yaml` file that defines several parameters.
The following example is based on the official installation guidance and is a starting point for your deployment:

[source, yaml]
----
global:
  suseObservability:
    # Required: Your {stackstate-product-name} license key
    license: "<YOUR_LICENSE_KEY>"

    # Required: Base URL for {stackstate-product-name}
    # Use http://localhost:8080 if ingress is not configured yet
    baseUrl: "https://observability.example.com"

    # Required: Sizing profile
    # Available: trial, 10-nonha, 20-nonha, 50-nonha, 100-nonha,
    #            150-ha, 250-ha, 500-ha, 4000-ha
    sizing:
      profile: "50-nonha"

    # Required: Plain text admin password
    adminPassword: "<CHANGE_ME_TO_A_STRONG_PASSWORD>"
ingress:
  enabled: true
  ingressClassName: traefik
  annotations:
    traefik.ingress.kubernetes.io/router.entrypoints: websecure
    cert-manager.io/cluster-issuer: selfsigned-issuer
  hosts:
    - host: observability.example.com
  tls:
    - hosts:
        - observability.example.com
      secretName: suse-observability-tls
----

The `profile` value depends on the expected cluster size and telemetry load. Choose the value that matches your environment; the product documentation provides the sizing guidance for HA and non-HA deployments.

For smaller or lab environments, use a lower profile and reduce the size of the installation accordingly.

# end::values[]

# tag::install[]
=== Install {so}

Deploy the chart into a dedicated namespace:

[source, bash]
----
helm upgrade --install \
  --namespace suse-observability \
  --create-namespace \
  --values values.yaml \
  suse-observability \
  suse-observability/suse-observability
----

This installs the {so} stack in the `suse-observability` namespace and creates the required Kubernetes resources for the backend and UI.

[IMPORTANT]
====
The product documentation notes that upgrading or downgrading from HA to non-HA or vice versa is not yet supported. Use a single sizing profile that fits your expected workload before deploying the stack.
====
# tag::install[]

# tag::verify[]
=== Verify the deployment

After installation, verify that the pods, services, and ingress resources are available:

[source, bash]
----
kubectl get pods -n suse-observability
kubectl get svc -n suse-observability
kubectl get ingress -A | grep observability
----

If the cluster uses a load balancer or wildcard DNS, confirm that the configured `baseUrl` resolves correctly and that the browser can reach the {so} UI.

After installation, log in as the admin user with the password you selected.

# end::verify[]

# tag::ui[]
=== Exposing the UI

For a real deployment, expose the Observability UI through a supported Ingress or load balancer. The `baseUrl` value must match the external URL that users use to access the product.

The recommended configuration is:

* a DNS record or trusted FQDN
* a valid TLS certificate
* a reachable ingress or load balancer
* correct hostname resolution from the users' browsers

For a secure setup, use a certificate managed by your platform or a certificate issuer trusted by your users.

# tag::agent[]
=== Observing a {shyb} cluster

Once the cluster runs {so} successfully, the next step is to connect the cluster to be monitored to {so}.
This is typically done through the cluster registration or agent flow described in the {so} product documentation, depending on your installation model.

For the agent-based flow, the key requirements are:

* The cluster to be monitored can reach the {so} ingest URL.
* A valid service token is configured for the agent.
* The required firewall rules and TLS settings allow the agent's traffic.

This lets the cluster send telemetry to the monitoring cluster without exposing the workload cluster unnecessarily.

For a practical architecture, keep the following in mind:

* The {shyb} cluster remains the workload cluster.
* The monitoring cluster remains the observability cluster.
* The {shyb} cluster is connected to the observability platform by the supported registration or telemetry mechanism.
* Dashboards and alerts are defined centrally in the {so} stack.

This separation helps ensure that the monitoring stack is resilient, easier to back up, and easier to maintain independently from the {shyb} workloads.
# end::agent[]

# tag::add[]
=== Adding the {shyb} cluster into {so}
* After logging in to {so}, add a cluster.
* Enter the cluster name (in this example, `dme`) and click **Install**.
+
image::SAP-Edge_Observability_new_Instance.png[title={so} New Instance,scaledwidth=99%]
* {so} now waits for the observability agent to connect. Select the {shyb} cluster to find the StackState ingest URL and create a service token.
* There are multiple ways to install the agent into the cluster. This example uses Helm. The {so} UI provides the available methods and commands for your environment.
* Open a shell on the {shyb} cluster.

[source, bash]
----
 helm repo add suse-observability https://charts.rancher.com/server-charts/prime/suse-observability
 helm repo update
----

[source, bash]
----
export SERVICE_TOKEN=<YOUR_SERVICE_TOKEN_FROM_THE_UI>
helm upgrade --install \
--namespace suse-observability-agent \
--create-namespace \
--set-string "stackstate.apiKey=$SERVICE_TOKEN" \
--set-string 'stackstate.cluster.name'='dme' \
--set-string 'stackstate.url'='https://observability.example.com' \
--set 'nodeAgent.skipKubeletTLSVerify'=true \
--set 'otel.integrations.rancherAgent'=false \
suse-observability-agent suse-observability/suse-observability-agent
----

For the next steps and information about using {so}, see the link:https://documentation.suse.com/cloudnative/suse-observability/latest/en/k8s-getting-started.html[getting started documentation].

# end::add[]

# tag::baseline[]
=== Recommended baseline for {shyb} observability

For a typical {shyb} environment, use the {so} cluster to collect:

* Kubernetes pod and node health
* {istio} traffic and service topology
* Application errors, latency, and throughput.
* Infrastructure resource usage.
* Cluster-level events and alert conditions.

This gives you a centralized operational view of the {shyb} environment while keeping the actual {shyb} workload cluster focused on the application itself.

This chapter covers the installation of the cluster monitoring platform. For the final {shyb} registration and telemetry integration steps, follow the current {so} documentation for registering external Kubernetes clusters and configuring the observed application sources.

# end::baseline[]
