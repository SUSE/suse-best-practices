# tag::deploy[]

=== Deployment

This chapter describes how to deploy a basic {reg} without high availability.

WARNING: The example deployment uses self-signed certificates. 
Self-signed certificates present security risks in production environments.
We recommend using certificates signed by a trusted certificate authority (CA) in production environments.

Before starting the deployment, create a Kubernetes secret that stores the login credentials as described in the documentation at
link:https://documentation.suse.com/en-us/cloudnative/suse-private-registry/html/private-registry/pr-deployment.html#pr-deployment-kube-secrets[]

==== Gathering login information

Before deploying {reg}, gather the login credentials for the official SUSE registry and save them in a Secret in the Kubernetes cluster.

NOTE: For the most up-to-date deployment guide, see
link:https://documentation.suse.com/en-us/cloudnative/suse-private-registry/html/private-registry/pr-deployment.html#pr-deployment-kube-secrets[].

To retrieve login credentials, log in to {scc} and select the organization holding the Registry subscription.
Click _Proxies_ as shown in the image below:

image::SAP-Edge-Registry-SCC-Org.png[title=SCC Proxy,scaledwidth=99%]

The _Mirroring credentials_ section on the right discplays your user name and password:

image::SAP-Edge-Registry-SCC-Creds.png[title=SCC Proxy Credentials,scaledwidth=99%]

To reveal the password, click the eye icon. 
Ongoing, this guide refers to these credentials as _PRIVATE_REGISTRY_USERNAME_ and _PRIVATE_REGISTRY_PASSWORD_.

Next, save the _PRIVATE_REGISTRY_PASSWORD_ to a `password.txt` file.
To log in and verify that your credentials work, run the following command:

[source, bash]
----
head -1 ./password.txt | helm registry login registry.suse.com --username <PRIVATE_REGISTRY_USERNAME> --password-stdin
----

Create a namespace for the registry-related resources.

[source, bash]
----
kubectl create namespace <PRIVATE_REGISTRY_NAMESPACE>
----

The deployment requires an *imagePullSecret* saved in the previously created namespace:

[source, bash]
----
kubectl create secret docker-registry suse-registry \
  --namespace <PRIVATE_REGISTRY_NAMESPACE> \
  --docker-server=registry.suse.com \
  --docker-username=<PRIVATE_REGISTRY_USERNAME> \
  --docker-password=$(head -1 ./password.txt)
----

In this example, the secret is named _suse-registry_. The next chapter references this secret.


==== Deploying without high availability

Deploying without high availability is the most basic approach because it requires no keystore or database dependencies.

[IMPORTANT]
====
By default, the {reg} Helm chart allocates low storage capacity for the image registry volume, which can cause disk saturation. 
Before deployment, adjust this value based on application sizing requirements.

For more information about customizating storage sizes, see the official 
link:https://documentation.suse.com/cloudnative/suse-private-registry/html/private-registry/pr-helm-chart-override.html#helm-persistence-parameters[{reg} Persistence Parameters Documentation].
====

The following configuration shows example values for deploying the registry with Helm using a _NodePort_ service for exposure, 
including the persistence configuration parameter: 

[source, yaml]
----
expose:
  type: nodePort
  nodePort:
    annotations: {}
    labels: {}
    name: harbor
    ports:
      http:
        nodePort: 30002
        port: 80
      https:
        nodePort: 30003
        port: 443
  tls:
    auto:
      commonName: <PRIVATE_REGISTRY_FQDN> 
externalURL: https://<PRIVATE_REGISTRY_FQDN> 
harborAdminPassword: "<MY_PASSWORD>" 
imagePullPolicy: IfNotPresent
imagePullSecrets:
- name: suse-registry

persistence:
  persistentVolumeClaim:
    registry:
      size: "5Gi" # Adjust this size based on your requirements
----

WARNING: The example configuration creates a self-signed TLS certificate.
Self-signed certificates present security risks in production environments.
In production environments, we recommend using certificates signed by a trusted certificate authority (CA).

To actually deploy, save the preceeding configuration to a `values.yaml`.

# tag::proxy-cache-project[]
[#proxyRegistryProject]
==== Create a Proxy Cache Project

Configure the {reg} as a transparent proxy cache. 
This eliminates the need to manually transfer images or maintain replication rules. 
When the cluster requests an image, {reg} automatically fetches it from the source registry, caches it locally, and serves it seamlessly.

===== Create the Registry Endpoint

Before creating a Proxy Cache Project, define a Registry Endpoint that points to an external, upstream container registry. 
To do so, log in to your registry and perform the following steps:

1. Navigate to *Administration* -> *Registries*.
2. Click *NEW ENDPOINT*.
+
image::SAP-Edge-Registry-Create-Endpoint.png[title=Create Registry Endpoint,scaledwidth=99%]
3. Configure the following parameters:
   * *Provider*: `Docker Registry`
   * *Name*: A generic name (e.g., `source-registry-endpoint`).
   * *Endpoint URL*: The URL of the source registry where the images to be cached are located (e.g., `\https://<SOURCE_REGISTRY_URL>`).
   * *Access ID* / *Access Secret*: Your user credentials for the source registry.
4. Click *TEST CONNECTION* to validate, then click *OK*.

===== Create the Proxy Cache Project

After the Registry Endpoint is set up, create the Proxy Cache Project. To do so, perform the following steps:

1. Navigate to *Projects* and click *NEW PROJECT*.
+
image::SAP-Edge-Registry-Create-Project.png[title=Create Registry Project,scaledwidth=99%]
2. Enter a project name (for example, `proxy-cache-project`).
3. Enable the *Proxy Cache* toggle switch.
+
image::SAP-Edge-Registry-Proxy-Project.png[title=Enable Proxy Cache Configuration]
4. Select the previously created endpoint (for example, `source-registry-endpoint`) from the *Endpoint* dropdown menu.
5. Click *OK*.

[TIP]
====
*Tag Retention Policy:* When the project is created, navigate to *Configuration* > *Policy* to adjust retention rules (for example, to prevent deleting cached images or to apply custom criteria).
====

# end::proxy-cache-project[]

# tag::use-elm[]

=== Using {reg} with {elm}

To use {reg} with {elm}, configure the {rke} cluster running the {elm} workload and adjust the configuration of the Edge Node.

==== Configuring the {rke} cluster that hosts ELM

To avoid setting up multiple *imagePullSecrets* for each namespace, we recommend adding {reg} to the cluster configuration as described in <<rancherRegistries>>.
If you use self-signed certificates or a certificate signed by an unknown CA, select the _Skip TLS Verifications_ check box.

==== Adjusting ELM Edge Node

Opt in for "Replicate Container Images".
In the *Local Container Registry URL* field, enter the registry URL  and append the project name.
For example, if the registry is hosted at `example.com` and the project is named `my-eic-project`, enter `example.com/my-eic-project`.

Also, ensure to enable *Authentication*.
Then, enter the user name and password for the registry.

If you use a self-signed certificate, select *No-Trusted Certificate* and upload the certificate retrieved as described in <<elmRegistryProject>>.

image::SAP-Edge-Registry-ELM-Config.png[title=ELM enable private registry,scaledwidth=99%]

# end::use-elm[]
