# tag::oidc[]

[#oidc-setup]
== Setup {rancher} as an OIDC provider

[IMPORTANT]
====
You can use DEX with other OIDC providers, as also stated in https://dexidp.io/docs/connectors/
For this guide, we'll describe the usage with {rancher}.
====

{rancher} can be used as the OIDC provider for {dex}.
A full documentation for this can be found at:
link:https://ranchermanager.docs.rancher.com/how-to-guides/advanced-user-guides/configure-oidc-provider[]


=== Using {rancher}

To set it up, open your {rancher} and navigate to the *_Users & Authentication_* menu. You can find this menu at the bottom left side as displayed in the picture below:

image::SAP-Edge-Rancher-Dashboard-Users-Icon.png[title=Rancher Dashboard User Icon,scaledwidth=99%,opts=inline,Embedded]

Once there open the *OIDC Apps* in the left bar as illustrated here:

image::SAP-Edge-Users-OIDC-Tab.png[title=Rancher User OIDC Tab,scaledwidth=99%,opts=inline,Embedded]

On this page you can gather the *Issuer URL*, that you will need when configuring {dex}.
To allow your {dme} application to authenticate through {dex}, you'll need to create a new OIDC App.
Therefore, click on *Add Application* at the upper right corner, as shown below:

image::SAP-Edge-Rancher-OIDC-Menu.png[title=Rancher User Menu,scaledwidth=99%,opts=inline,Embedded]

You should now see the OIDC creation page, which looks as displayed in the image below:

image::SAP-Edge-OIDC-Create.png[title=Rancher User Menu,scaledwidth=99%,opts=inline,Embedded]

Here you'll need to enter a name for your OIDC app and add the callback URL.
The callback URL must be the {dex-server-URL}/callback and be used as the *redirectURL* for the {dex} Helm chart.

Once you hit the *Add Application* button, you'll see the overview page for you OIDC App, where the _Client ID_ and the _Client Secrets_ are displayed.
Those will be used to configure dex and be referenced in this guide as <clientID> and <clientSecret>


=== Using a manifest

You can also apply a manifest to your {rancher} local cluster to create a new OIDC app.
To do so, upload the following manifest using the {rancher} UI or save the content and use kubectl to upload it:

[source, yaml, subs="attributes"]
----
apiVersion: management.cattle.io/v3
kind: OIDCClient
metadata:
  name: sap-dme-dex-client
spec:
  description: "OIDC Client für {dme} Dex"
  redirectURIs:
    - "https://{dex-server-URL}/callback" # This must be used for the redirectURL later
  tokenExpirationSeconds: 3600
  refreshTokenExpirationSeconds: 86400
----

=== Gather the client secret

Rancher automatically generates a Kubernetes Secret in the cattle-oidc-client-secrets namespace for each OIDCClient resource. The Secret’s name matches the OIDCClient client ID. Initially, the Secret contains a single client secret.
To retrieve the client secret, you can query it using kubectl as followed:

[source, bash]
----
kubectl get secret <client-name> -n cattle-oidc-client-secrets -o jsonpath="{.data.client-secret-1}" | base64 -d
----

# tag::nginx[]

[#nginx-cert]
== Create the dex server certificate for Ingress (Only for nginx)

If you are using Nginx, you'll need a certificate for the incoming Ingress traffic.

[source, yaml]
----
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: dex-server-cert
  namespace: auth
spec:
  secretName: dex-server-tls-secret # <--- Put this name into your Helm values under `secretName`
  duration: 8760h
  renewBefore: 720h
  commonName: "dex-dex-idp.auth.svc.cluster.local"  # <--- Match your Dex service name in Kubernetes
  isCA: false
  privateKey:
    algorithm: RSA
    size: 2048
  usages:
    - server auth
  dnsNames:
    - "dex-dex-idp.auth.svc.cluster.local"   # <--- Match your Dex service name in Kubernetes
    - "<your-Dex-URL>"
  issuerRef:
    name: my-cluster-ca-issuer
    kind: ClusterIssuer
----

# tag::values[]
== Deploying {dex}

You're now set to deploy {dex}.
Create a file _values.yaml_ to store some configurations for the {dex} Helm chart.
The configuration might look like the following:

[source, yaml, subs="attributes"]
----
config: 
  issuer: https://{dex-server-URL}/ # This must match your dex server address
  oauth2:
    skipApprovalScreen: true
  # Refer to https://dexidp.io/docs/configuration/storage/#kubernetes-custom-resource-definitions-crds
  storage:
    type: kubernetes
    config:
      inCluster: true
  connectors:
  - config:
      clientID: &lt;clientID&gt;
      clientSecret: &lt;clientSecret&gt;
      issuer: https://{rancher-URL}/oidc
      insecureSkipVerify: true
      redirectURI: https://{dex-server-URL}/callback  # This must match your configured Callback URL for your OIDC app
      scopes:
      - openid
      - profile
      - email
      - groups
      userIDKey: sub
      userNameKey: email
      insecureEnableGroups: true  # Ensures that group information is included in the ID token for DM Edge access
    id: rancher-oidc
    name: Rancher Login
    type: oidc
    getUserInfo: true
  expiry:
    idTokens: 10m
    refreshTokens:
      validIfNotUsedFor: 15m # Define a value which is no shorter than 15 minutes (15m) and no longer than 24 hours (24h)
      absoluteLifetime: 24h
      disableRotation: false
      reuseInterval: 1m    
  # Register a UI application (DM Edge or your own custom UI application) with dex as a client
  staticClients:
  - id: sap-dm-edge-client # Define an ID for the UI application
    secret: "super-secret-password-shared-with-sap-dm" # Define a secure secret for the UI application
    name: 'SAP Digital Manufacturing for Edge Computing' # Define a meaningful name for the UI application
    # Callback URL for Dex to redirect the user post authentication
    redirectURIs:
      - https://edge-ui.{dex-server-URL}/callback
----

[IMPORTANT]
====
Make sure that the <clientID> and <clientSecret> are matching your configuration in <<oidc-setup>>.
Also make sure that your {dex-server-URL} matches the address the dex server will be available at.
====
# end::values[]

# tag::nginx_ingress[]

If you're planning to access {dex} through an Ingress controller, you can add the following excerpt to your _values.yaml_, which will create and configure the Ingress for {dex}:

[source, yaml]
----
ingress:
  enabled: true
  className: nginx
  hosts:
    - host: <your-Dex-URL>
      paths:
        - path: /
          pathType: Prefix
  tls:
    - hosts:
        - <your-Dex-URL>
      # Specify the secret you created previously for the Dex server certificate
      secretName: dex-server-tls-secret
----

IMPORTANT: Make sure the secretName matches the secretName configured in <<nginx-cert>>.

# tag::cert[]
== Create a secret for dex

Next, we'll create a "dummy" certificate used to deliver the Root ca.crt into the dme namespace. SAP DM Edge mounts this secret so it can mathematically verify that the OIDC tokens handed out by DEX are legitimate and signed by a trusted source.

[source, yaml]
----
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: dex-ca-bundle
  namespace: dme
spec:
  secretName: dex-ca-secret
  commonName: "dummy-dex-ca"
  duration: 8760h
  isCA: false
  issuerRef:
    name: my-cluster-ca-issuer
    kind: ClusterIssuer
----

# tag::istio[]

== When using Istio

If you're using Istio and want to leverage it to route to your {dex} instance, you'll need to configure the related Istio routes.
Therefore, you'll need a dedicated Gateway to specify your DNS and certificate.
Furthermore a VirtualService will define that all incoming traffic through the gateway will be routed to your {dex} service.

Store the following configuration in a file _dex_istio.yaml_:

[source, yaml]
----
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: dex-gateway
  namespace: auth # Deploy in the same namespace as DEX
spec:
  selector:
    istio: ingressgateway # Must match the name of the Istio gateway pod
  servers:
    - hosts:
        - <your-Dex-URL>
      port:
        name: https
        number: 443
        protocol: HTTPS
      tls:
        credentialName: tls-secret
        mode: SIMPLE
---
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: dex-route
  namespace: auth # Deploy in the same namespace as DEX
spec:
  hosts:
    - "<your-Dex-URL>"
  gateways:
    - dex-gateway # Must match the gateway used by the wildcard service
  http:
    - match:
        - uri:
            prefix: /dex
      route:
        - destination:
            host: dex-dex-idp.auth.svc.cluster.local # Your actual internal DEX service K8s DNS
            port:
              number: 5556 # Your DEX service port
----

[NOTE]
====
If you followed the guide and have configured {metallb} and {istio}, the value of <your-Dex-URL> may be a subdomain of your <LB-address>.
E.g. if your <LB-address> is _192.168.1.66.sslip.io_, the <your-Dex-URL> may be _dex.192.168.1.66.sslip.io_.
====

Now apply the manifests to create the resources in your Kubernetes cluster:

[source, bash]
----
kubectl apply -f dex_istio.yaml
----

=== To verify reachability (optional)

If you want to verify if your deployed {dex} is working as expected, you can use the following commands:

[source, bash]
----
kubectl get secret dex-ca-secret -n dme -o jsonpath='{.data.tls\.crt}' | base64 -d > client.crt
kubectl get secret dex-ca-secret -n dme -o jsonpath='{.data.tls\.key}' | base64 -d > client.key
kubectl get secret dex-ca-secret -n dme -o jsonpath='{.data.ca\.crt}' | base64 -d > ca.crt

curl -v -i \
  --cacert ca.crt \
  --cert client.crt \
  --key client.key \
  https://{dex-server-URL}/.well-known/openid-configuration
----

# tag::dme_config[]

When using your own {dex} instance, the Helm values for the deployment of {dme} must be adjusted accordingly.
When following this guide, your values might look like:

[source, yaml]
----
global:
    dex:
        useEmbedded: false
    dexIssuer: https://{dex-server-URL}
    dexCACertificate: dex-ca-secret
    dexClient:
        clientID: sap-dm-edge-client 
        clientSecret: super-secret-password-shared-with-sap-dm
    idpLogoutUrl: https:/{rancher-URL}/oidc/logout
----
